2. 해킹·XSS·세션 탈취 경로

심각 H-01. SVG/HTML 파일 업로드 → 같은 출처(weavo.art)에서 스크립트 실행 → 세션 탈취

현상
업로드 검사는 브라우저의 file.type.startsWith('image/')(js/common.js:1005) 뿐이라 image/svg+xml 이 통과하고, uploadImage()(js/common.js:621-629)는 파일 이름의 확장자를 그대로 쓰며 contentType 을 지정하지 않습니다. 서버 쪽(SQL)에는 MIME·크기 제한이 없고, 버킷 설정은 대시보드에만 있어 확인되지 않았습니다. 이미지 프록시 functions/img/[[path]].js 는 업스트림 응답 헤더를 그대로 복사해(new Response(upstream.body, upstream)) 원본 Content-Type 을 내보내고, X-Content-Type-Options·Content-Security-Policy·Content-Disposition 을 붙이지 않습니다. 운영에서 확인한 /img/artwork/…jpg 응답 헤더는 content-type 과 cache-control 둘뿐이었습니다(_headers 의 보안 헤더는 Functions 응답에 적용되지 않음). 버킷 이름도 경로에서 그대로 받아 고정되어 있지 않습니다.
영향
로그인한 사용자가 <script> 가 든 SVG 를 작품이나 아바타로 올리면 https://weavo.art/img/artwork/<uid>/….svg 에서 weavo.art 출처로 스크립트가 실행됩니다(<img> 안에서는 실행되지 않지만, 링크를 직접 열면 실행). 세션 토큰이 localStorage 에 있으므로(H-04) 링크를 누른 사람의 계정(관리자 포함)을 탈취할 수 있습니다. 작품 링크(art_link)에 이 주소를 넣어 유도할 수 있습니다. Storage API 를 직접 호출하면 text/html 도 올릴 수 있어 같은 결과입니다.
조치
  • 대시보드: artwork 버킷 → Allowed MIME types = image/jpeg, image/png, image/webp, image/gif, File size limit = 10 MB. (서버가 강제하는 유일한 층입니다.)
  • 프록시: 첫 세그먼트가 artwork 일 때만 통과, 확장자 허용 목록(jpg·jpeg·png·webp·gif·avif) 외 404, 응답 헤더에 X-Content-Type-Options: nosniff, Content-Security-Policy: default-src 'none'; sandbox, Content-Disposition: inline 추가, Content-Type 은 확장자 기준으로 고정.
  • 클라이언트: 허용 목록(jpeg/png/webp/gif) 검사와 contentType 명시. shrinkImageFile 처럼 캔버스로 다시 인코딩하면 형식 자체가 정규화됩니다.

높음 H-02. 사이트 전역 CSP 없음, 외부 스크립트에 SRI 없음(버전 미고정)

현상
_headers 는 X-Frame-Options·HSTS 만 두고 CSP 는 "보류" 로 주석 처리되어 있습니다(운영 응답에서도 CSP 없음, Permissions-Policy 없음). 30개 페이지가 cdn.jsdelivr.net/npm/@supabase/supabase-js@2(메이저만 고정), d3@7, topojson-client@3 을 integrity 없이 로드합니다. CSS 는 @import 로 Google Fonts·Pretendard 를 불러옵니다.
영향
H-01·H-03 같은 삽입 경로가 있을 때 CSP 가 마지막 방어선이 되는데 없습니다. CDN 사고·계정 탈취로 supabase-js 가 바뀌면 인증 토큰을 다루는 코드라 전 계정이 영향받습니다.
조치
_headers 에 CSP 도입(default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; connect-src 'self' https://kzvheplmtzjmzcxjkxub.supabase.co; img-src 'self' data: https://kzvheplmtzjmzcxjkxub.supabase.co https://lh3.googleusercontent.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://cdn.jsdelivr.net; font-src https://fonts.gstatic.com https://cdn.jsdelivr.net; object-src 'none'; base-uri 'self'; frame-ancestors 'self' — 인라인 스크립트(index.html 언어 리다이렉트, JSON-LD)는 nonce 또는 외부 파일로 옮긴 뒤 적용). CDN 은 정확한 버전으로 고정하고 integrity·crossorigin 추가, 또는 세 라이브러리를 /js/vendor/ 에 넣어 자체 호스팅(빌드 없이 가능, 새 CDN 도 아님). Permissions-Policy: camera=(), microphone=(), geolocation=() 추가.

높음 H-03. 작가 목록 페이지에서 아바타 URL 이 이스케이프 없이 속성에 삽입됨(저장형 XSS)

현상
js/artists.js:12 — `<img class="artist-card-avatar" src="${cdnUrl(p.avatar_url)}" alt="">` 를 innerHTML 로 넣습니다. avatar_url 은 본인이 REST 로 임의 문자열을 쓸 수 있는 컬럼이고(supabase_mosaic.sql:22 update grant), cdnUrl() 은 Supabase 주소가 아니면 그대로 돌려줍니다. 프로젝트의 escapeHtml() 은 큰따옴표를 이스케이프하지 않아(js/common.js:10-12) 감싸도 속성 문맥에서는 부족합니다.
영향
avatar_url 에 x" onerror="… 를 넣으면 /ko/artists·/en/artists 를 여는 모든 방문자의 브라우저에서 스크립트가 실행됩니다. 이 페이지 외에는 사용자 문자열을 전부 textContent 로 넣고 있어 이 한 곳이 유일한 예외입니다.
조치
document.createElement('img') 로 만들고 img.src = … 로 대입(속성 문맥 소멸). escapeHtml 에 "·' 이스케이프 추가. DB 에 avatar_url 형식 체크(https:// 로 시작, 허용 호스트: 자체 Storage·googleusercontent) 추가.

중간 H-04. 세션 토큰이 localStorage 에 저장됨(XSS 피해 증폭)

현상
js/supabase-client.js 는 옵션 없이 createClient 를 호출해 supabase-js 기본값(localStorage, 세션 유지)을 씁니다.
영향
스크립트 삽입이 한 번이라도 성립하면 액세스·리프레시 토큰을 그대로 읽어 세션을 복제할 수 있습니다. 근본 대책은 H-01~H-03 을 막는 것이며, 이 자체는 supabase-js 의 표준 구성입니다.
조치
H-01·H-02·H-03 우선. 추가로 관리자 계정은 별도 브라우저 프로필 사용, 로그아웃 습관화.

중간 H-05. 작품 이미지 URL 에 외부 주소가 허용됨(추적·외부 호스팅)

현상
mosaic_submissions.image_url·thumb_url·author_avatar_url 은 로그인 사용자가 insert 할 수 있는 컬럼인데 길이·형식 체크가 없습니다(supabase_mosaic_profile_pool.sql:53-55). 화면은 cdnUrl() 을 거쳐 그대로 img.src 에 넣습니다. js/project.js:404 는 url("…") 문자열에 따옴표 이스케이프 없이 넣습니다.
영향
공격자 서버의 이미지를 Weavo 화면에 띄워 방문자 IP·UA 를 수집하거나, 삭제 뒤에도 원본이 남는 외부 호스팅 이미지를 등록할 수 있습니다.
조치
DB 체크: 세 컬럼은 null 또는 https://kzvheplmtzjmzcxjkxub.supabase.co/storage/v1/object/public/artwork/% 로 시작(아바타는 googleusercontent 허용). cdnUrl() 은 허용 호스트 외에는 null 을 돌려 자리표시자를 그리게.

낮음 H-06. 서버 렌더링 메타 속성의 이스케이프를 런타임에만 의존

현상

조치
HTMLRewriter(lol-html)는 속성값을 이스케이프하는 것으로 알려져 있으나, 테스트 계정의 bio 에 "><svg onload=alert(1)> 를 넣고 /ko/artists/<이름> 의 응답 원문을 확인해 두기를 권합니다. 이중 방어로 replace(/"/g,'&quot;') 를 넣어도 무해합니다.

현상

3. 데이터 손실·작품 삭제 가능성

심각 L-01. 관리자 세션 하나로 모든 작품을 한 번에 삭제 가능 — 건수 제한·감사 기록·복구 수단 없음

현상
mosaic_submissions 삭제 정책은 행 단위 술어 auth.uid() = author_id or exists(… is_admin) 입니다(supabase_mosaic.sql:221-226). 관리자 토큰으로 DELETE /rest/v1/mosaic_submissions?id=neq.0 한 번이면 전 작품이 삭제되고, 연쇄로 조각·좋아요·댓글·컬렉션 항목·알림이 함께 사라집니다. 화면(js/admin.js)에 삭제 버튼을 두지 않은 것은 규범(CLAUDE.md 13절)일 뿐 DB 는 막지 않습니다. 소프트 삭제·감사 로그 테이블·내보내기 스크립트가 저장소 어디에도 없고, Supabase 일일 백업(Pro, 7일 보관)은 DB 만 대상이라 Storage 파일은 포함되지 않습니다.
영향
관리자 Google 계정 탈취, 관리자 PC 의 악성 확장, 실수로 실행한 스크립트 한 줄로 작가들의 작품 전체가 되돌릴 수 없이 사라질 수 있습니다. 이 서비스의 핵심 자산이므로 가장 먼저 다뤄야 할 항목입니다.
조치
  • 삭제 감사 + 속도 제한 트리거(작은 SQL): submission_deletions(id, author_id, deleted_by, deleted_at, row jsonb) 테이블에 BEFORE DELETE 로 행을 기록하고, 같은 사용자가 10분에 5건을 넘기면 예외. 계정 삭제(delete_own_account) 안에서는 세션 플래그(set_config('weavo.bulk_delete_ok','on',true))로 예외를 우회. 이 한 가지로 "한 번에 전부" 는 불가능해지고, 지운 행의 내용이 남아 복구 가능해집니다.

2. Hacking, XSS and session theft

Critical H-01. SVG/HTML upload → script runs on the weavo.art origin → session theft

Finding
The only upload check is the browser's file.type.startsWith('image/') (js/common.js:1005), which image/svg+xml passes; uploadImage() (js/common.js:621-629) keeps the extension from the file name and sets no contentType. There is no MIME or size limit in SQL, and the bucket settings live only in the dashboard (unverified). The image proxy functions/img/[[path]].js copies the upstream headers verbatim (new Response(upstream.body, upstream)), relaying the original Content-Type, and adds no X-Content-Type-Options, Content-Security-Policy or Content-Disposition. The live /img/artwork/…jpg response carried only content-type and cache-control (the security headers in _headers do not apply to Functions responses). The bucket name is taken from the path and is not pinned.
Impact
A signed-in user who uploads an SVG containing <script> as an artwork or avatar gets it served at https://weavo.art/img/artwork/<uid>/….svg, where the script runs on the weavo.art origin (not inside <img>, but yes when the link is opened directly). Because the session token lives in localStorage (H-04), whoever clicks the link — admins included — can have their account taken over. The address can be planted in an artwork link (art_link). Calling the Storage API directly also allows text/html, with the same result.
Fix
  • Dashboard: artwork bucket → Allowed MIME types = image/jpeg, image/png, image/webp, image/gif, File size limit = 10 MB. (This is the only layer the server enforces.)
  • Proxy: pass only when the first segment is artwork; 404 for extensions outside jpg/jpeg/png/webp/gif/avif; add X-Content-Type-Options: nosniff, Content-Security-Policy: default-src 'none'; sandbox, Content-Disposition: inline; set Content-Type from the extension.
  • Client: an allowlist check (jpeg/png/webp/gif) and an explicit contentType. Re-encoding through a canvas, as shrinkImageFile does, normalises the format itself.

High H-02. No site-wide CSP; external scripts without SRI (versions not pinned)

Finding
_headers sets only X-Frame-Options and HSTS; CSP is commented out as "deliberately left out for now" (the live response has no CSP and no Permissions-Policy). Thirty pages load cdn.jsdelivr.net/npm/@supabase/supabase-js@2 (major version only), d3@7 and topojson-client@3 without integrity. CSS pulls Google Fonts and Pretendard through @import.
Impact
When an injection path such as H-01 or H-03 exists, CSP is the last line of defence, and it is missing. A CDN incident or account compromise that alters supabase-js — the code that handles auth tokens — affects every account.
Fix
Add a CSP in _headers (default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; connect-src 'self' https://kzvheplmtzjmzcxjkxub.supabase.co; img-src 'self' data: https://kzvheplmtzjmzcxjkxub.supabase.co https://lh3.googleusercontent.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://cdn.jsdelivr.net; font-src https://fonts.gstatic.com https://cdn.jsdelivr.net; object-src 'none'; base-uri 'self'; frame-ancestors 'self' — move the inline scripts (the language redirect in index.html, JSON-LD) to a nonce or external files first). Pin the CDN libraries to exact versions with integrity and crossorigin, or self-host the three libraries under /js/vendor/ (no build step needed, and not a new CDN). Add Permissions-Policy: camera=(), microphone=(), geolocation=().

High H-03. The artists page inserts the avatar URL into an attribute unescaped (stored XSS)

Finding
js/artists.js:12 — `<img class="artist-card-avatar" src="${cdnUrl(p.avatar_url)}" alt="">` is assigned through innerHTML. avatar_url is a column the owner can set to any string through REST (supabase_mosaic.sql:22 update grant), and cdnUrl() returns non-Supabase values unchanged. The project's escapeHtml() does not escape double quotes (js/common.js:10-12), so wrapping it would still be insufficient in an attribute context.
Impact
Setting avatar_url to x" onerror="… runs a script in the browser of every visitor of /ko/artists and /en/artists. Everywhere else user strings go through textContent; this is the single exception.
Fix
Build the element with document.createElement('img') and assign img.src = … (no attribute context). Extend escapeHtml to escape " and '. Add a DB check on avatar_url (starts with https://; allowed hosts: own Storage and googleusercontent).

Medium H-04. Session tokens are stored in localStorage (amplifies any XSS)

Finding
js/supabase-client.js calls createClient with no options, so the supabase-js defaults apply (localStorage, persistent session).
Impact
Any successful script injection can read the access and refresh tokens and clone the session. The real remedy is closing H-01 to H-03; this on its own is the standard supabase-js configuration.

Prioritise H-01, H-02 and H-03. Additionally, use a separate browser profile for admin accounts and sign out routinely.

Medium H-05. Artwork image URLs may point to external hosts (tracking, off-site hosting)

3. Data loss and artwork deletion

Critical L-01. One admin session can delete every artwork at once — no count limit, no audit trail, no recovery

Finding
The delete policy on mosaic_submissions is a per-row predicate, auth.uid() = author_id or exists(… is_admin) (supabase_mosaic.sql:221-226). With an admin token, a single DELETE /rest/v1/mosaic_submissions?id=neq.0 removes every artwork, cascading to pieces, likes, comments, collection items and notifications. Keeping delete buttons out of the admin page (js/admin.js) is a convention (CLAUDE.md §13); the database does not enforce it. There is no soft delete, no audit table and no export script anywhere in the repository, and Supabase's daily backups (Pro, 7 days) cover the database only — not Storage files.
Impact
A hijacked admin Google account, a malicious extension on an admin's PC, or one accidentally run line of script can erase all of the artists' work irreversibly. This is the service's core asset and should be addressed first.
Fix
  • Deletion audit + throttle trigger (small SQL): record each deleted row in submission_deletions(id, author_id, deleted_by, deleted_at, row jsonb) from a BEFORE DELETE trigger, and raise when the same user exceeds 5 deletions in 10 minutes. Inside account deletion (delete_own_account) bypass with a session flag (set_config('weavo.bulk_delete_ok','on',true)). This alone makes "everything at once" impossible and keeps the deleted rows recoverable.
  • Soft delete (medium): a deleted_at column, deleted_at is null in the public select policy, an admin restore tool, purge after 30 days.
  • Storage backup: an offline script (outside the repository, on an admin PC) that periodically downloads the whole artwork bucket with the service key. The database has Pro backups; consider adding PITR.
  • Two-factor authentication on admin Google accounts; keep admins to a minimum.

High L-02. Any signed-in user can pull other people's pieces out of the mosaic in bulk — unmatch_submissions

Finding
supabase_mosaic_rematch.sql:70-119. The file's own comment says it is callable by "any signed-in user"; 5,000 ids per call, no call-rate limit, and the only guard is an RGB distance above 15 (which the comment itself calls "coarse … NOT the real match-quality test"). That is far looser than the real placement threshold (Lab 20), so most correctly placed pieces pass it.
Impact
One account calling it repeatedly keeps campaigns empty (rows survive and return to the pool, but the screen goes blank). Whatever matching refills can be pulled out again.
Fix
The function is now used only by the server cleanup (release_poor_matches, security definer): revoke execute … from authenticated. The client fallback (releasePoorlyMatchedPieces in js/matching.js) already ignores errors, so nothing breaks.

High L-03. Any signed-in user can force other people's pieces into cells of their choosing — commit_pool_matches

Finding
supabase_mosaic_profile_pool.sql:65-129. It checks only "is the piece in the pool, is the cell open, are there duplicates" — no ownership check and no colour check (re-verified). Being security definer it also bypasses RLS.
Impact
Waiting pieces can be planted in arbitrary cells to draw patterns or words on the mosaic. The 6-hourly cleanup undoes it, but it can be repeated.
Fix
Server-side matching exists now, so revoke execute … from authenticated (the client fallback is used only when the RPC is missing). If it must stay, verify s.author_id = auth.uid() and a distance within piece_match_distance() per assignment.

High L-04. The table-level insert grant on mosaic_submissions was never revoked — rate-limit bypass and forged pieces

Finding
Nothing revokes grant insert on public.mosaic_submissions to authenticated from supabase_mosaic.sql:207 (re-verified); later column-level grants only add to it. A signed-in user can therefore insert created_at, parent_id, piece_row/col/n, home_project_id, match_tried_at and even id directly. The rate-limit trigger counts a 10-minute window by created_at and skips rows that have a parent_id.
Impact
① Backdating created_at or filling parent_id makes the 20-per-10-minutes limit meaningless. ② A piece row whose parent_id is someone else's artwork gets placed by matching, and clicking that cell opens the victim's artwork (the attacker's 16 px image shown as the victim's work). ③ id collisions and home_project_id manipulation.
Fix
One SQL file: revoke insert on public.mosaic_submissions from authenticated; then grant only the needed columns: grant insert (author_id, author_name, author_avatar_url, image_url, thumb_url, micro_thumb, avg_r, avg_g, avg_b, art_title, art_material, art_completed_date, art_description, art_link). Add parent_id is null and piece_n is null to the upload insert policy (pieces only via the RPC). Review profiles the same way (L-09).

High L-05. Any signed-in user can claim every open cell and halt matching, and lock cells forever with a future timestamp

Finding
The regular-user update policy on mosaic_pixels (supabase_mosaic_versions.sql:44-65) lets anyone turn a filled = false cell into filled=true, claimed_by=me; claimed_at is granted too but never validated. Claims older than 10 minutes can be reset by others, but a future claimed_at is "under 10 minutes" forever. Cells that already hold artwork cannot be touched (safe).
Impact
One REST call (update … .eq('filled', false)) claims every open cell in every campaign, leaving new pieces nowhere to go; only the admin policy can undo it.
Fix
Now that uploads go through the pool and server matching, client-side cell claiming is unused. Remove the regular-user update policy and grant; cover the two remaining uses (sweeping stale claims, resetting a cell after deleting one's own artwork) with a trigger (reset_pixel_on_submission_delete already does the latter) and an admin RPC. If it must stay, add claimed_at <= now() and a per-user claim cap to with check.

High L-06. The cleanup's wait interval is chosen by the caller — the 6-hour throttle can be nullified or monopolised

Finding
release_poor_matches(p_min_interval) and claim_rematch_slot(p_min_interval) use the argument as given. Just as the admin "apply colour match to all" passes '0 seconds', anyone can, and repeated calls can keep consuming the global slot so legitimate cleanups never run.
Fix
Inside release_poor_matches, for non-admins set p_min_interval := greatest(p_min_interval, interval '6 hours'). claim_rematch_slot is internal — revoke execute.

Medium L-07. Repeated calls to the piece-cutting and matching RPCs cause DB load and hold the global lock

Finding
set_submission_pieces can be called without limit on one's own artwork; each call takes the global advisory lock and deletes and re-inserts up to 144 rows (the rate-limit trigger does not count piece rows). match_pool_artworks can also be called repeatedly by any signed-in user (capped at 1,500 pieces per call). Both share the same lock key.
Fix
Add a per-artwork cut cooldown to set_submission_pieces (e.g. 60 s, admins exempt) via a pieces_cut_at column. For match_pool_artworks, a per-user calls-per-minute cap (a small mosaic_meta-style counter) or, longer term, a Cloudflare front proxy.

Medium L-08. When the admin who created a campaign deletes their account, the campaign cascades away or the deletion fails

Finding
mosaic_projects.created_by … references auth.users(id) on delete cascade (supabase_mosaic.sql:42). delete_own_account() deletes the auth.users row, so every campaign that admin created becomes a cascade target; if the artworks' (project_id is null) = (pixel_id is null) check trips mid-way, the whole account deletion rolls back. Neither outcome is intended.
Fix
Make created_by nullable with on delete set null (artworks and cells untouched). Campaigns belong to the site, not to an individual admin, so this is the right semantics.

High L-09. Re-running supabase_profiles.sql would let every signed-in user make themselves admin

Finding
The only protection of is_admin is the "revoke table-wide grant + column-level grants" in supabase_mosaic.sql:17-22 (no trigger, no policy). Yet supabase_profiles.sql:62 still contains grant insert, update on public.profiles to authenticated;, so running that file once more would make update({ is_admin: true }) succeed. Both files are written as "safe to re-run", so this is a realistic mistake.
Fix
Replace line 62 of supabase_profiles.sql with column-level grants. As defence in depth, add a BEFORE UPDATE trigger on profiles that raises when new.is_admin <> old.is_admin in a session that has an auth.uid() (i.e. via the API).

Medium L-10. Deleted artworks' images remain in Storage and the one-year cache; account deletion's file cleanup is incomplete

Finding
Deleting an artwork removes only the DB row (js/lightbox.js:639-650; no Storage delete call). Anyone who knows the URL can keep viewing it through /img/ (cached for a year). During account deletion, deleteMyStorageFiles() (js/auth.js:504-512) removes only the first page of the listing, ignores errors, and the account is deleted anyway — after which no principal is left to delete the remaining files. This can contradict the "uploaded images are deleted" wording on the deletion page.
Fix
Delete the owner's files (original and thumbnail) from the client when an artwork is deleted; record admin deletions in a cleanup queue table processed by an admin tool. Page through the whole listing during account deletion and abort with a message if cleanup fails. Purge /img/ cache entries for reported images from the Cloudflare dashboard.

4. Spam, automation and mass upload of obscene material

Critical S-01. Uploads go public instantly with no review, and there is no hide, suspend or emergency-stop tool

Finding
An upload appears immediately in the home page's recent artworks (5), the artwork browser, the campaign mosaic (auto-placed), the artist profile, the share image (OG) and the sitemap. mosaic_submissions has no hidden/status column, profiles has no suspend or upload-block flag, and accumulated reports (reports) never hide anything automatically. An admin can only "delete" or "remove from campaign" (which the next matching pass undoes). The "uploads locked" site option exists only as a comment example, not as code.
Impact
With one Google account, 20 obscene or hateful images per 10 minutes (multiplied by accounts) show up within seconds in the home hero mosaic and in share previews. Deleting leaves the files and caches behind (L-10), and the same account can upload again immediately.
Fix
  • Review status column: status text default 'approved' check (status in ('pending','approved','hidden')). Public select policy, matching, sitemap and SSR use approved only. A site option moderateNewUploads (uploads from accounts younger than N days or with fewer than N approved works become pending) enforced by an insert trigger.
  • Admin tools: a review queue (approve/hide), hide an artwork (not delete — no conflict with §13), hide and block uploads per artist (profiles.upload_blocked checked in the insert policy). Hiding is reversible, so misjudgements cost nothing.
  • Auto-hide on reports: a trigger sets hidden once three distinct reporters have flagged a work, pending admin review.
  • Emergency switch: check the uploadsOpen site option in the upload insert policy (turning it off in the admin page blocks all uploads immediately).
  • Automatic screening (optional): run an NSFW classifier (e.g. nsfwjs) in the browser before upload. It needs a new CDN, so per CLAUDE.md §2 introduce it only after approval and CSP updates, or self-host the model.
  • Bot protection (optional): Cloudflare Turnstile on upload and comment forms (external script, needs approval), Cloudflare WAF Bot Fight Mode.

High S-02. The upload rate limit can be bypassed and scales with the number of accounts

Finding
The only server limit is 20 uploads per 10 minutes per artist, and L-04 bypasses it. There is no daily cap, no per-IP limit and no CAPTCHA; sign-up is Google/Apple OAuth, so the limit grows linearly with accounts (if email sign-up is enabled in the dashboard, mass account creation becomes easier — verify O-02).
Fix
After fixing L-04: a daily cap (e.g. 50), a separate cap for new accounts (under 24 hours, e.g. 5), and the Storage bucket size limit (H-01). Keep email sign-up disabled.

Medium S-03. No rate limits on comments, reports, likes or follows; comment notifications are not collapsed

Finding
Artwork comments (1,000 characters) have no frequency limit and each creates a notification (only like and follow notifications are collapsed by a unique index). Reports are one per target but not rate-limited. The unused legacy tables profile_comments, cell_comments and cell_likes are still live with grants and no length limits, so REST can insert into them without bound.
Fix
Triggers: comments 10 per 10 min, reports 5 per 10 min, like/follow toggles 60 per 10 min. Collapse notifications by (recipient, actor, artwork, type) within a 5-minute window. Revoke insert on the legacy tables (or drop them).

Medium S-04. Blocking (user_blocks) is enforced server-side in one place only — comments

Finding
The insert policy stops a blocked user from commenting on the blocker's artworks, and nothing else: likes, follows, adding to collections and profile comments are not blocked. List hiding is a client filter that REST bypasses, and mosaic cells show blocked users regardless (by design). The block list is read once at sign-in.
Fix
Add the same block condition to the like and follow insert policies. Refresh myBlockedIds right after blocking.

Low S-05. Abuse room in visit counting and unbounded list queries

Finding
record_visit() can be called without limit by anyone, anonymous included (statistics inflation). The artists and network pages query everything without fetchAllRows and are silently truncated at 1,000 rows. The campaign page fetches the whole artwork row per filled cell (select *, about 0.9 KB per piece), reaching several MB per view once cells fill up (the composite-image cache task reported earlier).
Fix
Per-IP limits on record_visit are hard, but enforce once-per-day server-side for members. Use fetchAllRows for list queries. Trim the campaign cell columns and add the composite image cache.

5. User data exposure

High P-01. Every column of the profiles table is readable anonymously — disability data, real names, admin flag, city

Finding
Reading profiles?select=* with the anon key on the live site returns name (the Google real name, still present for older sign-ups), disabilities (an array of disability tags), city, links and is_admin. The select policy is using (true) with no column restriction (supabase_profiles.sql:44-46, 61).
Impact
Disability status is sensitive personal data. Even where members chose to display it, being able to download the whole membership in one REST call is a separate problem. is_admin lets anyone enumerate admin accounts — the starting point of targeted phishing (luring them to an H-01 link).
Fix
revoke select on public.profiles from anon, authenticated; then column-level grant select (id, username, avatar_url, bio, country_id, links, created_at). Owners and admins get the full row through an RPC or a separate policy. Return disabilities only where the profile page uses it and only when a consent flag (show_disabilities) is on, via a view. name is no longer used — null the old values. Serve the admin list through an admin RPC.

Low P-02. Likes and follows are fully public

Finding
Who liked what (mosaic_submission_likes) and who follows whom (user_saves) are readable in full anonymously (by design, stated in comments). Notifications, reports, block lists and visit statistics are properly private.
Fix
If intended, state "likes and follows are public" in the privacy policy (follows are mentioned; likes need checking). To make them private, restrict like reads to the owner plus the aggregate (like_count).

Low P-03. Privacy policy does not match the code

Finding
There is an Apple sign-in button, but the policy mentions Google only. It says the name is received, but the code no longer stores it (over-disclosure; old rows still hold real names). The promise to delete files on account deletion may not hold because of L-10. The policy does not say profile columns are fully readable anonymously.
Fix
Add Apple, fix the name wording, state what is public (profile fields, likes, follows), and align the deletion wording with the L-10 fix.

8. What already works well (keep)

  • is_admin is locked by column-level grants, and every admin RPC re-checks is_admin inside the function. Admins can only be appointed via SQL.
  • Artwork edits are owner-only; deletion is owner or admin (per row); even an admin cannot delete other people's auth accounts or Storage originals.
  • Campaign deletion and reshape return artworks to the pool instead of deleting them (FK on delete set null plus a check constraint as a double safeguard).
  • User strings go through textContent everywhere except one place (H-03); links pass safeHref (http(s) only) and carry rel="ugc nofollow noopener noreferrer". JSON-LD escapes <.
  • Notifications, reports, block lists and visit statistics are private; there are no secrets (service keys) in the repository; no open redirects and no inline event handlers.
  • HSTS, X-Frame-Options, nosniff and Referrer-Policy are present on page responses, and upload rate limits plus text length limits exist as DB triggers and checks (only their bypass paths need closing).
  • A privacy policy and an account-deletion page exist, and self-service account deletion is implemented as a server RPC.
