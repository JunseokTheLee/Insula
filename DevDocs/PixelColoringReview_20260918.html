Weavo 숫자 색칠(픽셀 아트) 게임 도입 검토

작성일 2026-09-18 · 대상 weavo.art (저장소 Insula, 커밋 b6225a8 기준) · 작성 Claude · 참고 게임: Easybrain Pixel Art – 숫자 색칠게임 책(Google Play, 1억+ 다운로드, 평점 4.7) · 오른쪽 위 버튼으로 영어 번역과 라이트/다크 테마를 바꿀 수 있습니다.
이 문서는 검토 결과만 담고 있습니다 — 코드는 수정하지 않았습니다. 근거는 ① 참고 게임의 스토어 설명과 최근 리뷰, ② 위보의 기존 게임 코드(js/game.js 1,240줄, supabase/supabase_game.sql 941줄)와 색 엔진·이미지 헬퍼, ③ 운영 DB 의 실제 규모(원작 26점·회원 36명·캠페인 1개), ④ 실제 작품 3점을 브라우저에서 픽셀 아트로 변환해 본 실험(3절)입니다.

한 줄 결론. 작가 작품을 숫자 색칠 판으로 자동 변환하는 것은 지금 코드 기반으로 충분히 가능하고, 변환 품질도 실험으로 확인했습니다(48칸·16색이면 원작의 구도와 색감이 살아 있음). 기존 "조각 찾기" 게임의 화면 골격(캔버스·확대·이동·탭 판정·바텀시트·효과음)과 색 엔진(rgbToLab, imageToColorGrid)을 그대로 쓰면 되고, 새로 만드는 것은 팔레트·칠하기 상호작용·판 저장·진행 저장·완성 화면입니다. DB·전송량 영향은 무시할 수준입니다.

권장안. ① 별도 페이지 /{lang}/coloring 로 만들고 게임 메뉴에서 두 게임을 함께 안내 ② 판은 업로드 시 브라우저가 한 번 만들어 DB 에 저장(pixel_boards, 작품당 약 3KB) — 모두 같은 판을 칠하게 되어 진행 동기화·완성 수가 일관됨 ③ 순위·시간 경쟁은 넣지 않음 — 완성한 사람 수와 내 완성 갤러리, 작가에게 보내는 완성 알림으로 대신함 ④ 작가 보호: 면책조항에 변환 이용 문구 추가 + 작품별 "색칠 게임에 쓰지 않음" 옵트아웃 ⑤ 광고·구매·부스터 판매·시즌 이벤트는 도입하지 않음(CLAUDE.md 의 금액 금지 규칙과 앱스토어 심사).

결정이 필요한 것 (9절에 상세)

  1. 도입 여부와 우선순위 — 권장: 도입, 조각 찾기 다음의 두 번째 게임
  2. 작가 동의 방식 — 권장: 약관 문구 + 작품별 옵트아웃(기본 허용)
  3. 순위 도입 여부 — 권장: 없음
  4. 별도 페이지 vs 게임 페이지 안의 탭 — 권장: 별도 페이지
  5. 기본 격자·색 수 — 권장: 긴 변 48칸 · 16색 (관리자 옵션)
  6. 비로그인 플레이 — 권장: 허용(진행은 브라우저에만 저장)
  7. 작가 완성 알림 — 권장: 켬, 사람·작품당 1회, 하루 상한

1. 참고 게임 분석 — Easybrain "Pixel Art: 숫자 색칠게임"

스토어 설명(2026-09-07 갱신)과 최근 한국어 리뷰를 읽었습니다. 핵심은 숫자가 적힌 격자를 팔레트의 같은 번호 색으로 탭해 채우는 단순한 규칙이고, 그 위에 콘텐츠 양(4만 장·매일 추가), 사진→픽셀 변환기(난이도 조절), 부스터(컬러 스플래시·요술봉), 타임랩스 공유, 시즌 이벤트·정원 메타, 3D 색칠, 광고·인앱 구매·프리미엄을 얹은 구조입니다.

리뷰에서 배울 점

  • 광고가 몰입을 깬다 — 위보는 광고가 없으니 그대로 강점.
  • 이동하려고 살짝 눌렀는데 칠해진다 — 탭과 이동을 구분하는 거리 임계값이 필요. 조각 찾기 게임의 dist() 로직이 이미 이 문제를 풀어 두었음.
  • 칸이 많은 그림은 남은 칸을 찾기 어렵고 힌트가 모자란다 — 무료 "다음 칸 찾기" 힌트, 축소하면 남은 칸이 도드라지는 표시(칠한 칸은 실제 색, 안 칠한 칸은 회색)로 대응.
  • 잠긴 그림이 너무 많다 — 위보는 잠금 없음.
  • 로그인이 없어 진행이 사라진다 — 위보는 계정 저장. 비로그인은 브라우저 저장 후 로그인 시 합침.

2. 위보에 맞는 콘셉트

참고 게임은 "그림"이 익명의 스톡 이미지입니다. 위보에서는 작가의 실제 작품이 판이 되므로 게임의 의미가 달라집니다 — 남의 그림을 한 칸씩 다시 그려 보는 감상 방식이 되고, 완성하면 원작(썸네일)이 드러나며 작가 프로필로 이어집니다. 조각 찾기 게임이 "캠페인 모자이크 안에서 작품을 찾는" 캠페인 중심 게임이라면, 색칠 게임은 캠페인과 무관하게 모든 작품이 대상이 되는 작품 중심 게임입니다.

  • 작가에게 돌아가는 것: "OOO님이 회원님의 작품 '제목'을 색칠로 완성했어요" 알림, 작품별 완성 수 표시. 업로드 동기가 됩니다.
  • 접근성: 조작이 탭 하나이고 시간 제한·경쟁이 없어, 속도를 겨루는 조각 찾기보다 폭넓게 참여할 수 있습니다(장애인·비장애인 아티스트가 나란히 참여하는 사이트의 지향과 맞음). 번호가 항상 있으므로 색 구분에 의존하지 않습니다.
  • 완성물은 새 작품이 아닙니다. 갤러리·모자이크에 들어가지 않고, 플레이어 프로필의 "내가 색칠한 작품" 목록에 원작 링크와 함께만 남습니다(작가의 작품과 섞이지 않게).

3. 변환 실험 — 실제 작품 3점

운영 DB 의 최근 원작 중 3점의 480px 썸네일(사이트가 이미 쓰는 thumb_url)을 브라우저(헤드리스 Chrome)에서 변환했습니다. 방법은 캔버스 축소 → 미디언 컷으로 팔레트 추출 → 칸마다 가장 가까운 색 번호 배정이며, 라이브러리 없이 약 60줄입니다. 저장소에는 넣지 않았습니다(스크래치 폴더).

관찰

  • 32칸은 구름·능선의 형태가 뭉개져 원작을 알아보기 어렵습니다. 48칸·16색이면 구도·빛·색감이 살아 있고, 64칸·24색은 원작에 가깝지만 칸이 3,000개를 넘어 한 판이 길어집니다(참고 게임의 진행 속도로 어림하면 1,728칸 ≈ 10~20분, 3,072칸 ≈ 30분 이상).
  • 팔레트에 구분이 어려운 비슷한 색이 생깁니다(회색 2·4번, 갈색 11·12번). 실제 구현에서는 Lab 공간(rgbToLab)에서 자르고 거리 ΔE 가 작은 색끼리 병합해야 "같은 색으로 보이는 두 번호" 문제가 없습니다.
  • 변환은 1~4ms 라 어디서 해도 부담이 없습니다 — 업로드 순간에 하든, 플레이 순간에 하든.
  • 적합성 판정이 필요합니다. 흰 그림·단색·극저대비 작품은 색칠 판이 될 수 없으므로, 병합 후 색이 6개 미만이거나 한 색이 판의 90% 이상이면 자동 제외합니다(기준은 관리자 옵션).
부수 발견. 작품 id 2298 "Morning Geometry 2026"(2026-09-16 업로드)은 원본 파일 자체가 2550×3300 의 완전한 흰 이미지(49KB)입니다. 썸네일이 깨진 것이 아니라 업로드가 빈 스캔으로 보입니다. 관리자 "작품" 탭에서 확인해 보시길 권합니다. 이 검토와는 별개 사안입니다.

4. 기술 설계

4.1 변환 파이프라인 (브라우저, 외부 라이브러리 없음)

  1. 원본이 아니라 thumb_url(긴 변 480px)을 /img/ 프록시로 읽습니다 — 같은 출처라 캔버스에서 읽을 수 있고(조각 만들기와 같은 조건), 엣지 캐시를 탑니다. 64칸이어도 칸당 7.5px 이상이라 충분합니다.
  2. 긴 변 n칸(기본 48)으로 축소해 칸별 색을 얻습니다 — color-engine.js 의 imageToColorGrid 와 같은 원리(투명 칸 제외 포함).
  3. Lab 공간에서 미디언 컷으로 k색(기본 16) 팔레트를 뽑고, ΔE < 기준(기본 8)인 색은 병합합니다.
  4. 칸마다 가장 가까운 팔레트 색의 번호를 배정합니다. 밝은 색부터 1번(참고 게임 관례).
  5. 적합성 판정: 색 수·최대 색 비율 기준에 못 미치면 "판 없음".
  6. 결과: { w, h, palette:[[r,g,b],…], cells: base64(Uint8Array) } — 1,728칸이면 약 2.6KB.

4.2 판을 어디에 둘 것인가 — 두 방식

A. 플레이할 때마다 변환(저장 없음)B. 한 번 만들어 DB 에 저장 (권장)
구현가장 단순. SQL 없음SQL 파일 1개(pixel_boards + RPC). 업로드 직후 브라우저가 만들어 저장하고, 옛 작품은 관리자 "픽셀 판 생성"(썸네일·조각 도구와 같은 패턴)
일관성브라우저·기기마다 캔버스 축소 결과가 미세하게 달라 사람마다 판이 조금 다를 수 있음. PC 에서 시작해 휴대폰에서 이어 하면 번호가 어긋날 수 있음모두 같은 판. 진행 동기화·완성 수·공유가 일관됨
옵션 변경다음 플레이부터 자동 반영(진행 중이던 판과 충돌)새 업로드부터 적용, 기존 판은 관리자 "전체 다시 생성"(조각과 같은 정책). 판에 version 을 두어 옛 진행을 무효화
DB0작품당 약 3KB (1만 작품에 30MB)

1단계 MVP 는 A 로 시작해도 되지만, 진행을 서버에 저장하는 순간 B 가 필요하므로 처음부터 B 로 가는 것을 권장합니다.

4.3 플레이 화면

기존 game.js 에서 가져올 것: 스테이지·캔버스 크기 예산(휴대폰 5M·PC 12M 픽셀), fitAll/zoomBy(커서 기준 확대)/cellAt(탭 → 칸), 핀치·드래그와 탭의 구분(dist()), 미니맵, 휴대폰 바텀시트, 효과음(iOS 무음 스위치 대응 포함), 컨페티(reduced motion 존중), Escape 종료, 게임 중 body.game-playing 상태.

새로 만들 것:

  • 팔레트 바 — 번호·색·남은 칸 수, 선택 상태. 선택한 번호의 칸을 판에서 진하게 강조.
  • 칠하기 — 탭 한 번에 한 칸, 누른 채 끌면 연속 칠하기("칠하기 모드" 토글로 이동과 구분). 번호가 다른 칸을 누르면 옅게 칠하고 "틀림" 상태로 두어 나중에 고치게 함.
  • 확대 수준별 표시 — 축소 상태에서는 숫자를 숨기고 안 칠한 칸을 회색 음영(밝기만)으로, 칠한 칸은 실제 색으로. 확대하면 숫자. 캔버스 2장(색 층·숫자 층)으로 그리고 DOM 칸은 만들지 않음(3,000개 DOM 은 휴대폰에서 느림).
  • 완성 연출 — 칸 경계가 사라지며 원작 썸네일로 크로스페이드 → "작가의 원작"이 나타나는 엔딩. 완성 화면에 작가·작품 링크, 팔로우 버튼, 다른 작품 추천.
  • 접근성 — 확대 하한을 칸 44px 이상으로, 선택 색 강조, 번호 항상 표시(색약 무관). 키보드 조작(방향키·숫자키)은 3단계.

4.4 진행 저장

  • 로그인: pixel_progress 에 비트셋(1,728칸 = 216바이트 → base64 288자)으로 upsert. 저장 시점은 칸 40개마다·5초 유휴·pagehide/visibilitychange(iOS 리로드를 견디는 기존 원칙과 같음).
  • 비로그인: localStorage 작품별 키. 로그인하면 서버 진행과 합침(칸 수가 많은 쪽).
  • 목록에 "이어 하기 · 62%" 표시.

4.5 순위·기록 — 넣지 않기를 권장

참고 게임도 "시간 제한도 없고 경쟁할 필요도 없다"를 정체성으로 내세웁니다. 색칠에 시간을 재면 감상이 노동이 되고, 무엇보다 서버가 칠한 정확성을 검증할 수 없어(정적 사이트, 완료 선언은 클라이언트) 기록 경쟁을 넣는 순간 조각 찾기 게임과 같은 부정행위 방어 문제가 생깁니다(그 게임은 조각당 250ms 하한으로 겨우 막고 있음). 대신 완성한 사람 수(작품별), 내 완성 갤러리(프로필), 작가 완성 알림을 둡니다. 개인 완성 시간은 화면에만 표시(옵션).

5. 작가 권리·동의

현재 면책조항은 "작품을 제출해도 소유권이 이전되지 않으며, 공동 Weavo 와 공개 갤러리에 사본이 배치될 뿐"이라고만 적혀 있습니다. 픽셀 판은 원작을 축소하고 색을 줄인 파생 이미지이고, 색칠은 다른 사람이 작가의 그림을 다시 그리는 행위라서 작가에 따라 불편할 수 있습니다. 조각 찾기 게임이 이미 작품 조각을 쓰고 있어 방향은 같지만, 이용 범위를 명시하는 편이 안전합니다.

  1. 면책조항·개인정보처리방침(en/ko)에 문구 추가: "제출한 작품은 모자이크 배치, 썸네일, 게임(조각 찾기·숫자 색칠)을 위해 축소·픽셀 이미지로 자동 변환되어 표시될 수 있습니다."
  2. 작품별 옵트아웃: 작품 편집 화면에 "이 작품을 색칠 게임에 쓰지 않음" 체크박스(coloring_opt_out). 기본은 허용(옵트아웃 방식) — 옵트인이면 현재 26점 중 0점으로 시작해 게임이 비어 버립니다. 사용자 결정 사항.
  3. 플레이·완성 화면에 작가명·작품명·원작 링크를 항상 표시.
  4. 완성 카드 이미지(3단계)에 "원작: 작가명 · weavo.art" 표기.
  5. 완성물은 새 작품으로 등록되지 않음(갤러리·모자이크와 분리).

Weavo Color-by-Number (Pixel Art) Game Review

Written 2026-09-18 · Target weavo.art (repository Insula, at commit b6225a8) · Author Claude · Reference game: Easybrain Pixel Art: Color by Number (Google Play, 100M+ installs, rated 4.7) · The buttons at the top right switch the translation and the light/dark theme.
This document holds the review only — no code was changed. It is based on ① the reference game's store listing and recent reviews, ② Weavo's existing game code (js/game.js, 1,240 lines; supabase/supabase_game.sql, 941 lines) plus the colour engine and image helpers, ③ the real size of the production database (26 original artworks, 36 members, 1 campaign), and ④ an experiment that converted three real artworks into pixel art in the browser (section 3).

0. Summary

Feasible
About 40% of the existing game code is reusable
1–4 ms

0.2 %
Of the monthly egress allowance at 300 boards a day
6–9 days
All three phases (phase 1 MVP: 3–4 days)

One-line conclusion. Turning artists' artworks into colour-by-number boards automatically is well within reach of the current code base, and the experiment confirms the conversion quality (at 48 cells and 16 colours the composition and palette of the original survive). The "find the piece" game already provides the screen skeleton — canvas, zoom, pan, tap detection, bottom sheet, sound — and the colour engine provides rgbToLab and imageToColorGrid. What is new is the palette, the painting interaction, board storage, progress saving and the completion screen. The database and egress impact is negligible.

Recommendation. ① Build it as its own page, /{lang}/coloring, with the game menu pointing at both games ② Generate each board once, in the browser at upload time, and store it in the database (pixel_boards, about 3 KB per artwork) so everyone paints the same board and progress and completion counts stay consistent ③ No rankings or timed competition — show the number of people who finished, a personal gallery of finished boards, and a completion notification to the artist instead ④ Protect artists: add a clause on derived images to the disclaimer plus a per-artwork "don't use in the colouring game" opt-out ⑤ No ads, purchases, paid boosters or seasonal events (Weavo's no-money rule in CLAUDE.md and app-store review).

Decisions needed (details in section 9)

  1. Whether and when — recommended: yes, as the second game after "find the piece"
  2. Artist consent model — recommended: policy clause + per-artwork opt-out (allowed by default)
  3. Rankings — recommended: none
  4. Separate page vs a tab on the game page — recommended: separate page
  5. Default grid and palette — recommended: 48 cells on the long side · 16 colours (admin option)
  6. Anonymous play — recommended: allowed, progress kept in the browser only
  7. Artist completion notification — recommended: on, once per person and artwork, daily cap

1. The reference game — Easybrain "Pixel Art: Color by Number"

I read the store listing (updated 2026-09-07) and the recent Korean reviews. The core rule is simple: tap numbered cells to fill them with the palette colour of the same number. On top sit content volume (40,000 pictures, new ones daily), a photo-to-pixel converter with difficulty control, boosters (colour splash, magic wand), time-lapse sharing, seasonal events and a "garden" meta-game, 3D colouring, and ads, in-app purchases and a premium subscription.

Lessons from the reviews

  • Ads break the flow — Weavo has none.
  • A light touch meant to pan paints a cell instead — a distance threshold must separate taps from pans. The find-the-piece game's dist() logic already solves this.
  • Busy pictures make the remaining cells hard to find and hints run out — a free "find the next cell" hint, and a zoomed-out view where unpainted cells stand out (painted cells in their real colour, unpainted in grey).
  • Too many locked pictures — nothing is locked on Weavo.
  • No sign-in, so progress disappears — Weavo saves to the account; anonymous progress lives in the browser and merges on sign-in.

2. A concept that fits Weavo

In the reference game the pictures are anonymous stock images. On Weavo the boards are artists' real works, which changes what the game means — it becomes a way of looking, redrawing someone's picture one cell at a time, and on completion the original (the thumbnail) is revealed and leads to the artist's profile. Where find-the-piece is a campaign-centred game (finding artworks inside the campaign mosaic), colouring is an artwork-centred game that covers every artwork regardless of campaigns.

  • What the artist gets back: a notification — "OOO finished colouring your artwork 'Title'" — and a completion count on each artwork. A reason to upload.
  • Accessibility: one tap, no time limit, no competition — a wider audience than the speed-based find-the-piece game, in line with a site where artists with and without disabilities take part side by side. Numbers are always shown, so nothing depends on telling colours apart.
  • A finished board is not a new artwork. It never enters the gallery or the mosaic; it only appears in the player's profile under "artworks I coloured", with a link to the original, so it cannot be confused with the artists' works.

3. Conversion experiment — three real artworks

Three of the most recent originals in the production database were converted in headless Chrome from their 480 px thumbnails (the thumb_url the site already uses): canvas downscale → median-cut palette → nearest palette number per cell. About 60 lines, no library. Nothing was added to the repository (scratch folder only).

Observations

  • 32 cells smears clouds and ridgelines beyond recognition. 48 cells · 16 colours keeps the composition, light and palette; 64 · 24 is close to the original but passes 3,000 cells, so one board takes long (by the reference game's pace, 1,728 cells ≈ 10–20 min, 3,072 ≈ 30+ min).
  • The palette contains near-identical shades (greys 2 and 4, browns 11 and 12). The real implementation should cut in Lab space (rgbToLab) and merge colours whose ΔE is small, so two numbers never look like the same colour.
  • Conversion takes 1–4 ms, so it costs nothing wherever it runs — at upload or at play time.
  • A suitability check is required. Blank, single-colour and very low-contrast artworks cannot become boards; anything with fewer than six colours after merging, or one colour covering 90% of the board, is excluded automatically (thresholds are admin options).
Side finding. Artwork id 2298, "Morning Geometry 2026" (uploaded 2026-09-16), is itself a completely white 2550×3300 image (49 KB). The thumbnail is not broken — the upload looks like an empty scan. Worth a look in the admin "Artworks" tab. Unrelated to this review.

4. Technical design

4.1 Conversion pipeline (browser, no external library)

  1. Read thumb_url (480 px on the long side), not the original, through the /img/ proxy — same origin, so the canvas stays readable (the same condition piece-cutting relies on), and edge-cached. Even at 64 cells that leaves 7.5 px per cell.
  2. Downscale to n cells on the long side (default 48) for one colour per cell — the same idea as imageToColorGrid in color-engine.js, transparent cells excluded.
  3. Median cut in Lab space to k colours (default 16); merge colours with ΔE below the threshold (default 8).
  4. Give each cell the number of its nearest palette colour, lightest colour first (the reference game's convention).
  5. Suitability check: too few colours or one dominant colour → "no board".
  6. Result: { w, h, palette:[[r,g,b],…], cells: base64(Uint8Array) } — about 2.6 KB for 1,728 cells.

4.2 Where the board lives — two options

A. Convert on every play (nothing stored)B. Generate once, store in the database (recommended)
ImplementationSimplest. No SQLOne SQL file (pixel_boards + RPC). Built by the browser right after upload; older artworks get an admin "create pixel boards" button (same pattern as thumbnails and pieces)
ConsistencyCanvas downscaling differs slightly across browsers and devices, so people may get slightly different boards; a board started on a PC and resumed on a phone may have shifted numbersEveryone gets the same board; progress sync, completion counts and sharing stay consistent
Option changesTake effect on the next play (clashing with boards in progress)Apply to new uploads; existing boards via admin "regenerate all" (the same policy as pieces). A version on the board invalidates old progress
Database0About 3 KB per artwork (30 MB for 10,000 artworks)

A phase-1 MVP could start with A, but the moment progress is saved server-side B becomes necessary, so starting with B is recommended.

4.3 The play screen

Taken from the existing game.js: the stage and canvas pixel budget (5M on phones, 12M on desktops), fitAll/zoomBy (zoom about the cursor)/cellAt (tap → cell), the pinch/drag-versus-tap distinction (dist()), the minimap, the phone bottom sheet, sound (including the iOS silent-switch handling), confetti (respecting reduced motion), Escape to quit, and the body.game-playing state.

New:

  • Palette bar — number, colour, cells remaining, selection state; cells of the selected number highlighted on the board.
  • Painting — one cell per tap, or press-and-drag for continuous painting (a "paint mode" toggle keeps it apart from panning). A cell of another number is painted faintly and marked "wrong" for fixing later.
  • Zoom-dependent rendering — zoomed out, numbers are hidden and unpainted cells show as grey shading (lightness only) while painted cells show their real colour; zoomed in, numbers appear. Two canvases (colour layer, number layer) and no DOM cells (3,000 DOM nodes are slow on phones).
  • Completion — cell borders dissolve and the board cross-fades into the original thumbnail: the artist's work appears as the ending. The completion screen links the artist and the artwork, offers a follow button and suggests other artworks.
  • Accessibility — a zoom floor of 44 px per cell, selected-colour highlighting, numbers always visible (independent of colour vision). Keyboard control (arrows, number keys) in phase 3.

4.4 Saving progress

  • Signed in: upsert a bitset into pixel_progress (1,728 cells = 216 bytes → 288 base64 characters). Save every 40 cells, after 5 s idle, and on pagehide/visibilitychange (the existing "survive iOS reloads" principle).
  • Anonymous: a localStorage key per artwork, merged with the server copy on sign-in (the one with more cells wins).
  • The list shows "Resume · 62%".

4.5 Rankings and records — recommended: none

The reference game itself advertises "no time limit, no competition". Timing a colouring turns contemplation into labour, and above all the server cannot verify the painting (static site; the client declares completion), so adding a record race would bring back the same anti-cheat problem the find-the-piece game barely holds off with its 250 ms-per-piece floor. Instead: a completion count per artwork, a personal gallery of finished boards on the profile, and an artist notification. A personal completion time is shown on screen only (optional).

5. Artists' rights and consent

The disclaimer currently says only that submitting an artwork transfers no ownership and that "a copy is placed" in the community mosaic and the public gallery. A pixel board is a derived image — downscaled, colour-reduced — and colouring means other people redraw the artist's picture, which some artists may dislike. Find-the-piece already uses artwork pieces, so the direction is the same, but stating the scope of use is safer.

  1. Add to the disclaimer and privacy policy (en/ko): "Submitted artworks may be automatically converted into reduced and pixelated images for mosaic placement, thumbnails and games (find the piece, colour by number) and shown as such."
  2. Per-artwork opt-out: a checkbox in the artwork editor, "Don't use this artwork in the colouring game" (coloring_opt_out). Allowed by default — an opt-in model would start with 0 of the current 26 artworks and an empty game. User decision.
  3. Always show the artist's name, the artwork title and a link to the original on the play and completion screens.
  4. The completion card image (phase 3) carries "Original: artist · weavo.art".
  5. Finished boards are never registered as artworks (kept apart from the gallery and the mosaic).
