1. What Weavo is1. Weavo 란

Weavo is a collaborative art-mosaic community. Artists upload their own artwork; Weavo reads each piece's dominant color and automatically places it in the best-matching open cell across every active mosaic project. Nobody picks a project or a position — the full picture only comes into focus as more artists add theirs. Seen from afar it reads as one image; up close, every "tile" is somebody's complete, independently made artwork, shown at full size and credited to its artist.

The site describes this as a mosaic built in reverse: a normal mosaic starts from the finished image and cuts pieces to fit it, whereas Weavo starts with nothing but a color rule. People who have never seen each other's work make their pieces first, and the whole only appears once enough of them have gathered.

Weavo is meant as a space where artists with and without disabilities are connected side by side through their work, without distinction — regardless of who made a piece or how, every piece takes part as an equal part of the whole.

Weavo 는 여러 사람의 작품이 모여 하나의 큰 모자이크를 완성하는 협업 예술 커뮤니티입니다. 작가는 자신의 작품만 올리면 됩니다. Weavo 가 작품의 대표 색상을 읽어, 진행 중인 모든 프로젝트를 통틀어 색이 가장 잘 맞는 빈 칸에 자동으로 배치합니다. 프로젝트나 위치를 사람이 고르지 않으며, 작품이 쌓일수록 전체 그림이 서서히 드러납니다. 멀리서 보면 하나의 이미지지만, 가까이 가면 각 "타일"이 누군가가 완성한 독립된 작품이고, 원본 크기로 작가 이름과 함께 보입니다.

사이트는 이것을 "거꾸로 만들어지는 모자이크"라고 설명합니다. 일반 모자이크는 완성 이미지를 먼저 정하고 거기에 맞춰 조각을 만들지만, Weavo 는 색상 규칙 외에는 아무것도 정하지 않고 시작합니다. 서로의 작품을 본 적 없는 사람들이 먼저 각자의 작품을 만들고, 충분히 모인 뒤에야 전체 모습이 나타납니다.

Weavo 는 장애인 아티스트와 비장애인 아티스트가 구분되지 않은 채 작품으로 나란히 연결되는 공간을 지향합니다. 누가, 어떤 방식으로 만들었는지와 관계없이 모든 작품은 전체를 완성하는 동등한 하나의 조각으로 참여합니다.

2. How a mosaic comes together2. 모자이크가 만들어지는 과정

  1. An admin creates a project. A reference image is reduced to a grid of target colors (imageToColorGrid() in js/color-engine.js); one mosaic_pixels row is created per cell. Cells that fall on transparent parts of the reference are skipped entirely and stay as permanent gaps.관리자가 프로젝트를 만듭니다. 기준 이미지를 목표 색상 격자로 축소하고(js/color-engine.js 의 imageToColorGrid()), 칸마다 mosaic_pixels 행을 하나씩 만듭니다. 기준 이미지의 투명한 부분에 해당하는 칸은 아예 만들지 않아 영구적인 빈 자리로 남습니다.
  2. An artist uploads artwork from their profile (js/profile-view.js) into the Supabase Storage bucket artwork. No project is chosen and no tags are entered. The piece lands in mosaic_submissions with project_id/pixel_id empty — the artist's "pool".작가가 프로필에서 작품을 올립니다(js/profile-view.js). 파일은 Supabase Storage 의 artwork 버킷에 저장됩니다. 프로젝트 선택도, 태그 입력도 없습니다. 작품은 project_id/pixel_id 가 비어 있는 상태로 mosaic_submissions 에 들어갑니다 — 작가의 "풀(pool)" 입니다.
  3. The dominant color is computed in the browser. imageAverageColor() samples the image on a 48×48 grid, weighted by alpha, so transparent padding (common on uploaded PNGs) no longer drags the average toward black.대표 색상은 브라우저에서 계산합니다. imageAverageColor() 가 이미지를 48×48 격자로 샘플링하고 알파값으로 가중 평균을 냅니다. 업로드 PNG 에 흔한 투명 여백이 평균을 검정 쪽으로 끌어내리는 문제를 이렇게 피했습니다.
  4. Cross-project matching runs (runPoolMatching() in js/matching.js). Every pool piece, oldest upload first, claims the still-open cell closest to it by Lab color distance across all non-archived projects — but only if the match is good enough (POOR_MATCH_DISTANCE). The result is committed atomically by the commit_pool_matches RPC, which re-checks every assignment server-side because the browser's snapshot may already be stale.프로젝트를 가로지르는 매칭이 실행됩니다(js/matching.js 의 runPoolMatching()). 풀에 있는 작품이 오래된 업로드 순으로, 보관되지 않은 모든 프로젝트의 빈 칸 가운데 Lab 색거리가 가장 가까운 칸을 차지합니다 — 단, 매칭 품질이 기준(POOR_MATCH_DISTANCE)을 넘을 때만입니다. 결과는 commit_pool_matches RPC 가 원자적으로 기록하며, 브라우저의 스냅샷이 이미 낡았을 수 있어 서버에서 모든 배정을 다시 검증합니다.
  5. Since 2026-09-10 the matching pass itself runs inside the database (match_pool_artworks / release_poor_matches, supabase_mosaic_server_matching.sql): the browser only calls the RPC and gets back what was placed, instead of downloading every open cell. Cell target colors are also served as a per-version PNG (grid_image_url, supabase_mosaic_grid_image.sql) read through the /img/ cache, and the grid view draws them on one canvas with a DOM element only per filled cell. All three fall back to the previous behaviour until their SQL is applied.2026-09-10부터 매칭 계산은 DB 안에서 실행됩니다(match_pool_artworks / release_poor_matches, supabase_mosaic_server_matching.sql). 브라우저는 RPC 를 부르고 배치 결과만 받을 뿐 빈 칸 전체를 내려받지 않습니다. 칸의 목표색도 버전별 PNG(grid_image_url, supabase_mosaic_grid_image.sql)로 /img/ 캐시를 통해 읽고, 격자 뷰는 캔버스 한 장 + 채워진 칸만 DOM 으로 그립니다. 세 가지 모두 SQL 적용 전에는 이전 방식으로 폴백합니다.
  6. There is no server process or cron. Matching is triggered right after anything that changes either side of the match — a new upload, a new project's cells coming online, a reshape, or a piece being removed — from the page that caused it. A throttled cleanup pass (releasePoorlyMatchedPieces()) returns badly matched pieces to the pool at most once per 6 hours sitewide, guarded DB-side by claim_rematch_slot.서버 프로세스나 크론은 없습니다. 매칭은 매칭의 양쪽 중 하나가 바뀌는 순간 — 새 업로드, 새 프로젝트의 칸 생성, reshape, 작품 제거 — 그 동작을 일으킨 페이지에서 곧바로 실행됩니다. 색이 잘 맞지 않는 작품을 풀로 되돌리는 정리 작업(releasePoorlyMatchedPieces())은 사이트 전체에서 6시간에 한 번만 돌며, claim_rematch_slot 이 DB 쪽에서 동시 실행을 막습니다.

Supabase
  • Postgres with RLS + RPCsPostgres (RLS + RPC)
  • Auth (Google / Apple sign-in)Auth (Google / Apple 로그인)
  • Storage bucket artworkStorage 버킷 artwork
  • The browser talks to Supabase directly with the public anon key (js/supabase-client.js). Every permission is enforced by RLS policies and column-scoped grants, not by application code.브라우저가 공개 anon 키로 Supabase 에 직접 접속합니다(js/supabase-client.js). 모든 권한은 앱 코드가 아니라 RLS 정책과 컬럼 단위 grant 가 강제합니다.
  • Multi-step writes go through RPCs that re-validate on the server: commit_pool_matches, reshape_mosaic_project, unmatch_submission(s), delete_mosaic_project, delete_own_account.여러 단계로 이루어진 쓰기는 RPC 를 거칩니다. 서버에서 다시 검증합니다: commit_pool_matches, reshape_mosaic_project, unmatch_submission(s), delete_mosaic_project, delete_own_account.
  • Images never hit Supabase egress twice per edge. cdnUrl() in js/common.js rewrites Storage URLs to /img/<bucket>/<path>; functions/img/[[path]].js fetches the object once and caches it at the Cloudflare edge for a year.이미지는 엣지마다 Supabase 에서 한 번만 가져옵니다. js/common.js 의 cdnUrl() 이 Storage URL 을 /img/<bucket>/<path> 로 바꾸고, functions/img/[[path]].js 가 객체를 한 번 받아 Cloudflare 엣지에 1년간 캐시합니다.
  • The Android app is a Trusted Web Activity pointed at the same site (.well-known/assetlinks.json, package art.weavo.app).Android 앱은 같은 사이트를 감싼 Trusted Web Activity 입니다(.well-known/assetlinks.json, 패키지 art.weavo.app).

10. Local development & deployment10. 로컬 실행 · 배포

There is nothing to build. To serve the site locally together with the Pages Functions, _headers and _redirects:

npx wrangler pages dev .

wrangler is already present under node_modules/. Pages that don't rely on a Function can simply be opened as files. .wrangler/ (local account cache) is git-ignored.

wrangler 는 node_modules/ 에 이미 들어 있습니다. Function 이 필요 없는 페이지는 파일을 직접 열어도 됩니다. .wrangler/(로컬 계정 캐시)는 git 에서 제외돼 있습니다.

After changing JS or CSS, bump the asset version. Every page links scripts and stylesheets as /js/x.js?v=YYYYMMDD-HHMMSS; node tools/bump-asset-version.js re-stamps all of them with one new second-resolution value, so a deploy uses new URLs and the year-long cache never serves stale or mixed files. The versioned pre-commit hook runs it automatically once a clone has enabled it with git config core.hooksPath tools/git-hooks. JS 나 CSS 를 고치면 자산 버전을 올립니다. 모든 페이지가 스크립트·스타일을 /js/x.js?v=YYYYMMDD-HHMMSS 형태로 링크하며, node tools/bump-asset-version.js 가 전부를 초 단위의 새 값 하나로 다시 찍습니다. 배포마다 URL 이 바뀌므로 1년 캐시가 옛 파일이나 섞인 파일을 내주지 않습니다. 버전 관리되는 pre-commit 훅이 자동으로 실행하며, clone 마다 한 번 git config core.hooksPath tools/git-hooks 로 켭니다.

Pushing to main on GitHub deploys to production. The repository is connected to the Cloudflare Pages project weavo through the Cloudflare GitHub app: each commit gets a "Cloudflare Pages" check, and the production site is updated automatically.
