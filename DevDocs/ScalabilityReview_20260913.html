Weavo 확장성 점검 보고서

작성일 2026-09-13 · 대상 weavo.art (저장소 Insula) · 작성 Claude · 오른쪽 위 버튼으로 영어 번역과 라이트/다크 테마를 바꿀 수 있습니다.
이 문서는 운영 데이터베이스의 실제 응답을 측정하고(익명 키로 읽을 수 있는 범위, gzip 압축 후 전송 바이트), 브라우저에서 실제 연산 비용을 계측하고(겹침 해소 알고리즘·SVG 갱신), 코드를 읽어 작성했습니다. 데이터를 바꾸거나 코드를 수정하지 않았습니다. 전송량은 모두 gzip 압축 후, 즉 Supabase 요금제가 실제로 세는 기준입니다.

0. 요약

지금 규모(회원 34명, 작품 28점)에서는 어느 항목도 한계에 가깝지 않습니다. 다만 한계가 오는 방식이 두 종류로 갈리며, 그중 하나가 위험합니다.

작품 수약 5,000점용량이 아니라 캠페인 운영과 사이트맵. 용량 한계는 13만 점대

가장 중요한 한 가지 — 회원이 1,000명을 넘으면 작가 목록과 네트워크 그래프가 오류 없이 일부 회원을 빠뜨립니다. Supabase가 응답을 1,000행에서 말없이 자르기 때문입니다. 사용자는 고장이 났다고 인식하지 못하고 자기 계정이 잘못됐다고 생각합니다. 고치는 데는 두 줄이면 됩니다.

2. 회원 수가 늘면

한계는 용량이 아니라 네트워크 화면에서 먼저 옵니다. 오는 순서대로 적습니다.

높음 ① 네트워크 그래프가 느려진다 — 200명부터

js/network.js의 resolveOrbitOverlaps()는 모든 노드 쌍을 비교하는 O(n²) 연산을 2회 반복해서, 매 프레임 실행합니다. 여기에 SVG 갱신이 더해집니다.

조용히 깨짐 ② 1,000명에서 목록과 그래프가 말없이 잘린다

Supabase(PostgREST)는 응답을 기본 1,000행에서 자르고 오류를 내지 않습니다. 저장소 규칙(CLAUDE.md 7절)이 fetchAllRows를 쓰도록 정해 두었지만, 두 곳이 쓰지 않고 있습니다.

  • js/artists.js:41 — 작가 목록이 profiles 전체를 limit 없이 조회
  • js/network.js:80 — user_saves와 profiles를 둘 다 전체 조회
사용자가 겪는 것1,001번째 회원부터 작가 목록과 그래프에서 사라집니다. 연결선도 일부만 그려져 실제보다 덜 연결된 것처럼 보입니다. 무엇보다 "내 네트워크" 버튼이 먹통이 됩니다 — 내 노드가 잘려 나가면 "아직 네트워크에 표시할 내 프로필이 없습니다"라는 안내만 나옵니다. 가입도 했고 팔로우도 했는데 그렇게 나옵니다. 왜 위험한가눈에 보이는 고장이 아니라 잘못된 정보를 조용히 보여주는 종류입니다. 겪는 사람은 서비스가 틀렸다고 생각하지 않고 자기 계정에 문제가 있다고 생각합니다. 운영자도 신고를 받기 전까지 알 수 없습니다. 전송량은?문제가 아닙니다. 1,000명이라도 압축 후 86KB입니다.

중간 ③ 전체 공지 발송이 회원 수만큼 호출된다

공지는 회원 한 명당 notifications 행 하나를 넣고, 기존 트리거가 행마다 Edge Function을 부릅니다(for each row). 기존 알림 경로를 그대로 재사용하는 설계라 안전하지만, 호출 수가 회원 수에 비례합니다.

현재34명 → 34회. 월 한도 200만 회 대비 무시할 수준 1만 명이면1만 회. 한도 자체는 여유가 있지만, 한 트랜잭션 안에서 pg_net 요청 1만 건이 큐에 쌓입니다.

여유 ④ Supabase MAU 한도

Pro 요금제 월간 활성 사용자 100,000명. 위 항목들보다 훨씬 뒤에 오는 한계입니다.

3. 작품 수가 늘면

건전한 부분

인덱스는 잘 설계되어 있습니다. (created_at desc, id desc) where parent_id is null 부분 인덱스가 작품 목록 정렬을 정확히 덮고, (project_id, x, y) 유니크 인덱스가 칸 조회를 해당 캠페인 범위로 가둡니다. 격자 이미지(15KB PNG)는 /img/ 엣지 캐시를 타므로 데이터베이스 전송량을 거의 쓰지 않습니다. 쿼리 성능은 병목이 아닙니다.

4. 네트워크 화면 — 사용자가 겪는 것

가장 먼저 한계가 오는 화면이므로 따로 정리합니다. 오는 순서대로입니다.

  1. 회전이 끊긴다 — 200명부터 미세하게, 모바일 500명·PC 1,000명에서 명확히. 부드럽게 도는 것이 이 화면의 전부인데 그게 깨집니다.
  2. 터치·클릭 반응이 늦다 — 계산이 메인 스레드를 점유해 노드를 눌러도 한 박자 늦게 반응합니다.
  3. 휴대폰이 뜨거워지고 배터리가 닳는다 — 화면을 켜 둔 내내 초당 60회 계산이 돕니다. 멈추는 것은 노드를 선택했을 때뿐입니다.
  4. 진입이 느리다 — 아바타를 회원 수만큼 동시에 요청합니다. 게다가 31개 중 27개가 구글 등 외부 URL이라 /img/ 엣지 캐시를 타지 않습니다. 1,000명이면 외부 이미지 요청이 약 900개입니다. (파일 자체는 평균 2.4KB로 작습니다 — 문제는 크기가 아니라 요청 수입니다.)
  5. 화면이 의미를 잃는다 — 기술 문제 이전에, 1,400px 화면에 노드 500개를 그리면 서로 겹쳐 이름을 읽을 수 없습니다. 성능이 버텨도 볼 수 없는 그림이 됩니다.
  6. 1,000명을 넘으면 틀린 그림을 조용히 보여준다 — 2장 ②에 적은 대로입니다.

5. 해결 방법

1순위 전체 조회에 fetchAllRows 적용

해결2장 ②의 조용한 잘림. 작가 목록과 네트워크가 1,000명 너머까지 정확해집니다 방법이미 저장소에 있는 fetchAllRows(common.js)로 감싸면 됩니다. 캠페인 칸 조회가 이미 같은 방식을 씁니다 작업량두 줄 수준. 지금 해 두는 것을 권합니다 — 고치지 않으면 1,000명째부터 아무 신호 없이 틀린 화면이 시작됩니다

2순위 겹침 해소를 공간 격자(grid bucket) 방식으로

해결회전 끊김, 반응 지연, 발열 — 2장 ①의 전부 방법지금은 모든 쌍을 비교하지만, 노드를 화면 격자 칸에 나눠 담고 같은 칸과 이웃 칸만 비교하면 됩니다. 노드는 자기 반지름보다 먼 상대와는 어차피 겹칠 수 없습니다. O(n²) → O(n), 1,000명 기준 12ms → 1ms 미만 작업량함수 하나 교체. 바깥에서 보면 동작이 같으므로 영향 범위가 좁습니다 시점회원 200명 전. 늦게 하면 "느려졌다"는 신고를 받은 뒤가 됩니다

3순위 전체 보기의 범위를 바꾸기 — 가장 본질적

해결4장 ⑤. 성능과 가독성을 동시에 방법전체 네트워크를 한 화면에 그리는 것은 수백 명이 넘으면 성능과 무관하게 쓸모가 없어집니다. 회원이 많아지면 기본을 "내 네트워크"로 두고, 전체 보기는 주요 연결자 중심의 개요로 바꾸는 편이 화면의 목적에도 맞습니다. 전환 버튼은 이미 있으므로 기본값과 전체 보기의 범위만 정하면 됩니다 작업량중간. 어디까지 보여줄지(상위 N명·2촌 이내 등)는 결정이 필요합니다

4순위 캠페인 상세의 (*) 조인을 필요한 컬럼만으로

해결캠페인 상세 전송량. 칸당 292B → 홈과 같은 171B 수준이면 만재 기준 1.46MB → 850KB 방법홈(project-preview.js)이 이미 필요한 컬럼만 지정해 받고 있습니다. 같은 방식으로 바꾸되, 라이트박스가 쓰는 컬럼이 빠지지 않는지 확인이 필요합니다 시점칸 사용률 50% 전

5순위 사이트맵 페이지 분할

해결작품 1,000점 이후 검색 노출 누락 방법사이트맵 색인(sitemap index)으로 나눠 여러 파일로 내보냅니다. 현재 코드에 1,000행 상한이 주석으로 명시되어 있어 의도된 임시 조치임이 기록돼 있습니다

6순위 그 밖에

  • 아바타를 /img/ 프록시 경유로 — 외부 URL 요청 900개를 엣지 캐시로. 외부 도메인 프록시 정책 검토가 필요합니다
  • 화면 밖 노드 갱신 생략(뷰포트 컬링) — 확대 중일 때 SVG 비용이 크게 줄어듭니다
  • 작품 탐색을 keyset 페이지네이션으로 — OFFSET 대신 "마지막으로 본 항목 이후"로 조회
  • SVG → Canvas 렌더링 — 수천 노드까지 가능해지지만 클릭 판정과 접근성을 다시 만들어야 합니다. 지금 하면 과잉이고, 수천 명이 현실이 됐을 때 검토할 일입니다

One setting halves the capacity — the site currently runs pieceGrid=5 (25 pieces per artwork). Raising it to the default 7 makes 49 pieces, which cuts a campaign's capacity from 199 artworks to 101 and raises DB cost per artwork from 36KB to roughly 70KB.

What's already sound

The indexes are well designed. A partial index on (created_at desc, id desc) where parent_id is null covers artwork listing exactly, and the (project_id, x, y) unique index confines cell reads to one campaign. The grid image (a 15KB PNG) is served through the /img/ edge cache and costs almost no database transfer. Query performance is not the bottleneck.

4. The network view — what users actually experience

This screen hits its limit first, so it gets its own section. In the order things arrive:

  1. The rotation stutters — faintly from 200 members, clearly at 500 on mobile and 1,000 on desktop. Turning smoothly is the entire point of this screen, and that is what breaks.
  2. Taps and clicks lag — the computation holds the main thread, so nodes respond a beat late.
  3. Phones get warm and drain — the work runs 60 times a second the whole time the screen is open. It only pauses while a node is selected.
  4. Entering is slow — avatars are requested one per member, and 27 of 31 are external URLs (Google and the like) that bypass the /img/ edge cache. At 1,000 members that is roughly 900 external image requests. (The files are small — 2.4KB on average. The problem is the number of requests, not their size.)
  5. The picture stops meaning anything — before performance even matters, 500 nodes on a 1,400px screen overlap into an unreadable mass. Even if it ran smoothly, there would be nothing to see.
  6. Past 1,000 it quietly shows a wrong picture — as described in §2 ②.

5. Fixes

First Use fetchAllRows for the unbounded reads

FixesThe silent truncation in §2 ②. The artist list and graph stay correct past 1,000 members HowWrap them in fetchAllRows, which already exists in common.js — campaign cell reads use it already EffortAbout two lines. Worth doing now: left alone, wrong screens begin at member 1,000 with no signal at all

Second Replace overlap resolution with spatial bucketing

FixesStutter, input lag, heat — all of §2 ① HowInstead of comparing every pair, sort nodes into grid cells and compare only within a cell and its neighbours — a node can't overlap anything further away than its own radius. O(n²) → O(n); at 1,000 members, 12ms → under 1ms EffortOne function swapped. Behaviour is identical from outside, so the blast radius is small WhenBefore 200 members. Later means after the complaints

Third Change what "Everyone" shows — the most fundamental fix

Fixes§4 ⑤ — performance and readability together HowDrawing the whole network at once stops being useful past a few hundred people regardless of performance. As membership grows, default to "My network" and make "Everyone" an overview built around the main connectors. The toggle already exists — only the default and the scope of "Everyone" need deciding EffortMedium. How much to show (top N, within two hops…) is a product decision

Fourth Narrow the campaign detail join from (*)

FixesCampaign transfer size: 292B per cell down toward the home screen's 171B — 1.46MB → ~850KB when full HowThe home screen (project-preview.js) already names its columns. Copy that, checking that nothing the lightbox needs is dropped WhenBefore cells are 50% full

Fifth Split the sitemap

FixesSearch coverage stalling past 1,000 artworks HowEmit a sitemap index pointing at several files. The current 1,000-row cap is written into the code as a comment, so it is a known, deliberate stopgap

Sixth Everything else

  • Route avatars through /img/ — turns ~900 external requests into edge-cached ones. Needs a decision about proxying third-party domains
  • Skip off-screen nodes (viewport culling) — large saving while zoomed in
  • Keyset pagination for browsing — "after the last item seen" instead of OFFSET
  • SVG → Canvas — would carry thousands of nodes, but click hit-testing and accessibility have to be rebuilt. Overkill today; revisit when thousands of members are real
